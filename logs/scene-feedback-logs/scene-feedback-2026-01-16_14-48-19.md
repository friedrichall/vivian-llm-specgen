## 2) Notable Data / Risks (from JSON)

1. **Missing colliders on key interactables**  
   - CoffeeButtons and WaterButtons have **no colliders**, so they are not clickable unless colliders are added.
2. **Negative scales** on some meshes (e.g., LeftOutlet/RightOutlet and SteamPipeHolder).  
   - Negative scales can break collider orientation, normals, and some physics assumptions. Prefer to keep colliders on parent objects with positive scale.
3. **Extremely heavy mesh**: `SteamOutlet/SteamPipe` has **192,512 triangles**.  
   - Avoid MeshCollider; keep it non-colliding or use a simplified collider.
4. **CoffeePlane collider exists** (MeshCollider) and is extremely thin (Y size ~0).  
   - Particle collision with a near-zero thickness plane may need careful collision settings.

## 3) Functional Requirements (Gameplay/Interaction)

### 3.1 Primary interaction object
- **CoffeeMachine2** — interaction type: **SCENE_JSON** (provided)
  - Treat CoffeeMachine2 as the root “appliance” entity.
  - All interaction and state is managed by a single controller on CoffeeMachine2 (or CoffeeMachine child).

### 3.2 User stories
1. **Power control**
   - User presses **OnOff** to toggle machine power.
   - Display updates to OFF/ON/READY states.
2. **Dispense coffee**
   - With power ON and cup present, user presses:
     - Strong coffee button → dispense from **both** outlets or a chosen outlet (configurable; default: both outlets but can be single-cup mode if cup centered).
     - Light coffee button → dispense as lighter/shorter pour.
     - Two light coffees button → dispense from both outlets simultaneously (CoffeeSimulation1 + CoffeeSimulation2).
3. **Feedback**
   - While dispensing: coffee particle effect plays; audio plays; display shows progress.
   - When done: particles stop; display returns to READY.
4. **Steam/hot water (optional)**
   - If implemented, pressing Steam/HotWater (after adding colliders) triggers alternate particle/visual and audio (steam/hot water), and uses the SteamOutlet.

## 4) State Machine

### 4.1 Machine States
- **OFF**
  - Inputs disabled except OnOff.
  - Display shows OFF.
- **BOOTING** *(optional short delay after OnOff)*
  - Display shows warming/initializing.
- **READY**
  - Accepts drink commands.
- **DISPENSING_COFFEE**
  - Coffee simulations active.
  - Optionally lock UI to prevent double-trigger.
- **ERROR**
  - Missing cup, or other checks fail.

### 4.2 Transitions
- OFF → (OnOff) → BOOTING → READY
- READY → (Coffee button) → DISPENSING_COFFEE → READY
- READY → (Coffee button, no cup) → ERROR (or show message) → READY after timeout
- READY → (OnOff) → OFF

## 7) Logic Rules / Validation

### 7.1 Cup presence rule
Cup is a separate object `CoffeeMachine2/Cup`.
- Machine should only dispense if:
  - Cup’s bounds intersect CupDockTrigger OR
  - Cup is parented/placed at dock position by setup.

If cup missing:
- Do not start particles
- Display error “PLACE CUP” briefly

### 7.2 Multi-cup rule
- **TwoLightCoffees**: require either
  - two cups detected (not present), OR
  - allow dispensing anyway as “two spouts into one area” (acceptable given only one cup model exists).  
Default spec: allow dispensing with one cup (no extra requirement), but emit from both spouts.

### 7.3 Power rule
- All drink buttons ignored in OFF state.
